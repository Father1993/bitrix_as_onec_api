# Обмен остатками и ценами с 1С

Production API: `https://mk-27.ru/local/tools/as_onec_api.php`.

Авторизация для 1С — заголовок `X-Stock-Import-Key`. Ключ в запросах, файлах 1С и логах не публиковать.

## Что работает

- Складской учёт включён: остаток хранится по паре товар + склад в `b_catalog_store_product`; Bitrix пересчитывает общий `CATALOG_PRODUCT.QUANTITY`.
- Справочник складов уже существует. На старте **не создавать** склады из 1С: сначала использовать согласованное соответствие внешнего кода 1С и существующего склада Bitrix.
- Цены записываются отдельно для каждого типа цены.
- Резерв (`QUANTITY_RESERVED`) этим API не меняется.

### Типы цен production

| Bitrix ID | Тип | Использование витриной |
|---:|---|---|
| 1 | Розничная Ф | Хабаровск, Владивосток, Благовещенск, Артём |
| 17 | Сахалин РОЗНИЦА | Южно-Сахалинск |
| 16 | Оптовые | Юрлица, кроме Сахалина |
| 2 | Сахалин ОПТ | Юрлица Южно-Сахалинска |

## Остатки

`POST ?path=/v1/stocks/import`

```json
{
  "items": [
    {
      "product_xml_id": "внешний-код-товара-из-1С",
      "store_xml_id": "внешний-код-склада-из-1С",
      "amount": 17
    }
  ]
}
```

Допустим также `store_id`, но для регулярного обмена предпочтителен стабильный внешний код склада. API принимает абсолютный остаток, а не приращение: повтор того же сообщения безопасен. Отсутствие товара или склада в сообщении ничего не обнуляет.

Проверка результата:

`GET ?path=/v1/stocks&xml_id=<внешний-код-товара>`

Успех: `failed: 0`; в ответе есть `stores[]`, `quantity_total` и `catalog_quantity`.

## Цены

`POST ?path=/v1/prices`

```json
{
  "items": [
    {
      "product_xml_id": "внешний-код-товара-из-1С",
      "catalog_group_id": 1,
      "price": 30112,
      "currency": "RUB"
    }
  ]
}
```

Передавать цену отдельной строкой для каждого нужного типа. Проверка:

`GET ?path=/v1/prices&xml_id=<внешний-код-товара>`.

## Порядок первого запуска 1С

1. Согласовать таблицу `внешний код склада 1С -> склад Bitrix`; исключить брак, транзит и склады «в пути», если они не должны влиять на витрину.
2. Отправить один товар на один согласованный физический склад и проверить GET-ответ.
3. Отправить небольшой пакет, убедиться, что в каждом ответе `failed` равно нулю.
4. Запускать регулярный обмен пакетами. При текущих настройках production применяются дефолты модуля: до 10 000 строк, 10 MiB тела, batch 100.

## Контроль обмена после запуска 1С

После установки версии с журналом каждый `POST`-ответ содержит `request_id`. Последние 200 операций без ключей и тел запросов доступны только с ключом API:

`GET ?path=/v1/audit/requests&limit=50`

Запись содержит время, IP клиента, операцию, HTTP-код, `total`, `updated`, `failed` и до пяти ошибок. Норма для очередного пакета остатков: `http_code=200`, `ok=true`, `failed=0`.

Для проверки одного товара используйте:

`GET ?path=/v1/stocks&xml_id=<внешний-код-товара>`

При складском учёте `stores[]` должен содержать позиции 1С, а `quantity_total` должен совпадать с суммой этих складов. Если виден только `catalog_quantity`, а `stores` пуст, обмен не записал остатки по складам.

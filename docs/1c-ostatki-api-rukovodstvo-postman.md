# Остатки через `as.onec_api`: руководство для 1С-программиста (Postman)

Коротко: как устроен обмен, что передавать, как проверить в Postman, на что смотреть в ответах. **Примеров кода на 1С нет** — только контракт HTTP и JSON, пригодные для ручной проверки.

---

## 1. Точка входа и маршруты

**Базовый URL (подставьте свой сайт):**

`https://ваш-сайт/local/tools/as_onec_api.php`

Маршрут передаётся **query-параметром** `path=` (без `path` API не знает, что вызывать).

| Назначение | Метод | `path` |
|------------|--------|--------|
| Прочитать остаток по товару | `GET` | `/v1/stocks` |
| Загрузить остатки в Битрикс | `POST` | `/v1/stocks/import` **или** `/v1/stocks` |
| Справочник складов / правка складов | `GET` / `POST` | `/v1/stores` |

`POST` на оба `path` остатков ведёт себя **одинаково**. Склады — см. [stores-api-postman.md](stores-api-postman.md).

**Альтернативы только для POST импорта (если договорились на уровне сервера):**  
`public/http_import.php` в составе модуля — тоже импорт остатков; в типовом сценарии удобнее всего **`/local/tools/as_onec_api.php?path=...`**.

---

## 2. Справочник складов: что может API, а чего нет

**Полный реестр складов сайта** (активных по умолчанию, до 500 записей) можно получить запросом **`GET /v1/stores`** с тем же ключом, что и для остатков. Один склад: query `store_id=…`, `store_xml_id=…` или `code=…`. Неактивные — с `include_inactive=1`. Подробно и с примерами Postman: [stores-api-postman.md](stores-api-postman.md). Создание/обновление записей склада: **`POST /v1/stores`** (там же в доке).

**Дополнительно на практике:**

1. **Соответствие «наш склад в 1С ↔ Битрикс»** можно сверить с админкой: **Магазин → Склады** — **ID**, **Символьный код (CODE)**, **Внешний код (XML_ID)**. Эти поля дублируются в JSON ответа `GET /v1/stores`.
2. **GET `/v1/stocks`** по товару при включённом складском учёте возвращает `stores` **только по тем складам, где у товара уже есть остаток** — для проверки «какой склад в обмене по позиции» удобен; для **полного** справочника используйте **`GET /v1/stores`**, а не только этот фрагмент.

---

## 3. Ключ доступа (обязательно согласовать)

В `local/php_interface/include/config.php` задаётся секрет, обычно константа **`ONEC_STOCK_IMPORT_ACCESS_KEY`** (и/или настройки модуля `as.onec_api` в админке). **Рабочий ключ выдаёт администратор** — в документ не вставляйте.

**GET:** достаточно **одного** варианта:

- заголовок `X-Stock-Import-Key: <ключ>`  
- **или** query: `access_key=<ключ>` (менее удобно, ключ виден в URL/логах).

**POST:** на практике удобнее **заголовок** `X-Stock-Import-Key`. Допустимо также:

- поле `access_key` **в корне JSON**, если тело — **объект** `{"items":[...], "access_key":"..."}`;  
- в корневом **массиве** тела `access_key` **нет** (массив — только список строк) → используйте заголовок.  
- пара `login` + `password` в корне JSON (как в модуле) — **только для POST**; для GET не подходит.

## 4. GET `/v1/stocks` — прочитать остаток

**Postman**

- **Method:** GET  
- **URL:** `{{base_url}}?path=/v1/stocks&xml_id=ВНЕШНИЙ_КОД_ТОВАРА`  
- **Headers:** `X-Stock-Import-Key: {{access_key}}`  

`xml_id` — это **внешний идентификатор элемента каталога** в Битрикс (тот же смысл, что `XML_ID` / внешний код номенклатуры в обмене с сайтом).

**Что важно в ответе**

- Включён **складской учёт** Битрикс, если `inventory_management: true` (в коде модуля также может быть `use_store_control` — смысл тот же флаг).  
- **Без складов** (`false`): смотрите поле **`quantity`** — итоговый остаток товара.  
- **Со складами** (`true`):
  - **`stores`** — остатки по складам (для привязки к импорту тут видны `store_id`, `store_xml_id`, `store_code` **для тех складов, где у товара уже есть движение/остаток**);
  - **`quantity_total`** — сумма `amount` по `stores`;
  - **`catalog_quantity`** — агрегат каталога (`QUANTITY` в карточке), **для витрины/карточки** удобнее ориентироваться на него;
  - **`quantity_total` может быть 0**, а **`catalog_quantity` > 0`**, пока по складам ещё не выровняли остатки — это не обязательно баг обмена.

**Типовые HTTP-коды:** `200` — успех; `400` — нет `xml_id`; `401` — нет/неверный ключ; `404` — товар не найден / не тот контур.

## 5. POST импорт — форма запроса

**Postman**

- **Method:** POST  
- **URL:** `{{base_url}}?path=/v1/stocks/import`  
- **Headers:** `Content-Type: application/json; charset=UTF-8`, `X-Stock-Import-Key: {{access_key}}`  
- **Body:** raw, JSON

**Два допустимых варианта тела**

1. **Объект** с массивом `items` (удобно добавить `access_key` в корень, если ключ не в заголовке):
   - `{"items":[ {...}, {...} ]}`

2. **Корневой массив** позиций (как в шпаргалке Postman):
   - `[ {...}, {...} ]`

**Одна строка массива = одна операция** «товар + количество + (при учёте по складам) один склад».  
Нельзя вложить «несколько складов» внутрь одного объекта — **для одного товара и трёх складов** в теле **три отдельных объекта** с **одинаковым** `product_xml_id` (или `product_id`) и **разными** `store_id` / `store_xml_id` / `store_code` и своим `amount`.

---

## 6. Поля одной позиции (строки `items`)

**Товар (нужен один из вариантов):**

- **`product_xml_id`** (предпочтительно для обмена с 1С) — внешний код элемента;  
- или **`xml_id` / `XML_ID`** — то же по смыслу;  
- или **`product_id`** — внутренний ID элемента в Битрикс, если 1С его уже хранит.

**Количество:**

- **`amount`** или **`quantity`**, число **≥ 0**, **дробь допустима**; отрицательные **нельзя**; **0** — остаток ноль.

**Склад** — **только если** на сайте **включён** складской учёт:

- **`store_id`** — числовой ID склада в Битрикс; **или**
- **`store_xml_id`** / **`store_code`** — внешний или символьный код склада (модуль ищет активный склад по `XML_ID` и `CODE`, плюс при необходимости сопоставление через проектные механизмы, например свойство «место хранения» в каталоге — детали на стороне внедрения).

**Если склад в строке не указан** и в настройках модуля задан **`default_store_id`**, подставится **он** (см. настройки `as.onec_api` / константа `ONEC_STOCK_IMPORT_DEFAULT_STORE_ID`). Для **реального** многоскладского обмена по разным площадкам **в каждой строке** указывайте конкретный склад — на «default» рассчитывать **нельзя**, если у вас больше одного склада.

---

## 7. Примеры тел для Postman (JSON)

**Один товар, без складского учёта на сайте (или везде уходит в default-склад по настройке):**

```json
{
  "items": [
    {
      "product_xml_id": "GUID-ИЛИ-ВНЕШНИЙ-КОД-ТОВАРА",
      "amount": 12.5
    }
  ]
}
```

**Один товар, три склада — один HTTP-запрос, три строки в `items`:**

```json
{
  "items": [
    {
      "product_xml_id": "GUID-ТОВАРА",
      "amount": 5,
      "store_id": 1
    },
    {
      "product_xml_id": "GUID-ТОВАРА",
      "amount": 0,
      "store_xml_id": "UUID-СКЛАДА-ИЗ-БИТРИКС"
    },
    {
      "product_xml_id": "GUID-ТОВАРА",
      "amount": 2,
      "store_code": "SIMVOLNYI_KOD_SKLADA"
    }
  ]
}
```

**Корневой массив (без обёртки `items`) — тот же смысл:**

```json
[
  {
    "product_xml_id": "GUID-ТОВАРА",
    "amount": 1,
    "store_id": 1
  }
]
```

(Для такого варианта ключ передавайте **только** заголовком, не в теле.)

## 8. Ответ POST: как понять, что обмен прошёл

Даже при **HTTP 200** смотрите тело:

| Поле | Смысл |
|------|--------|
| `ok` | Успех на уровне «запрос разобрали» |
| `total` | Сколько строк пришло |
| `updated` | Сколько строк **реально применили** |
| `failed` | Сколько строк **с ошибкой** |
| `errors` | Массив по проблемным строкам (часто есть `index`, текст `message`, при необходимости `product_xml_id` / `product_id`) |
| `errors_truncated` | `true` — ошибок слишком много, список обрезан; смотрите логи / дробите пакет |
| `inventory_management` | Режим складов на момент обработки |

**Если `failed > 0`**, часть остатков **не** записалась — разбирать `errors` обязательно.

**Типовые причины ошибок по строке:** пустой/не тот `product_xml_id` или дубли `XML_ID` у разных товаров в каталоге; `amount` не число или отрицательное; при складах — склад не найден, не передан, неактивен; неверный ключ; превышены лимиты.

---

## 9. Лимиты и тяжёлые пакеты

В настройках модуля `as.onec_api` (и/или в `config.php` константами `ONEC_STOCK_IMPORT_MAX_BODY_BYTES`, `ONEC_STOCK_IMPORT_MAX_ITEMS`, `ONEC_STOCK_IMPORT_BATCH_SIZE`) заданы ограничения на **размер тела** и **число строк**. При **HTTP 413** — уменьшить пакет. Внутри сервера обработка может идти **батчами** — внешне это один ответ, но **слишком большой** одним запросом лучше не слать.

## 10. Мини-сценарий внедрения (проверка в Postman)

1. Получить **ключ** и (при многоскладье) **таблицу складов** от администратора Битрикс.  
2. **GET** `/v1/stocks?xml_id=...` по одному известному товару — убедиться в `inventory_management` и в том, что товар находится.  
3. **POST** одну-две строки импорта, снова **GET** — сравнить `stores` / `quantity` с ожиданием.  
4. Потом включать регулярный обмен **пакетами** в пределах лимитов; мониторить **`failed`**, а не только HTTP-код.

---

## 11. Кому задать вопрос, если чего-то нет в API

- **Список складов и соответствие кодов** — **админка Битрикс** и владелец внедрения, а не «ещё один GET к API остатков».  
- **Смысл `catalog_quantity` vs `quantity_total`** — раздел 4 и README модуля.  
- **Почему строка не импортируется** — поле `message` в `errors[]` и отсутствие дублей `XML_ID` у товаров.
